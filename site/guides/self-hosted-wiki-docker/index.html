How do I self-host a team wiki with Docker?

Run a self-hosted wiki with Docker: what to decide first, how Turtle, Docmost, Outline, BookStack and Wiki.js compare to operate, and how to back up and update.

Try the demo Ask Jérémie by email
Jérémie ConstantBuilds Turtle at novalutions. Updated 27 November 2026.

Short answer

We build Turtle, so this guide is not neutral. We compare the operational footprint of five open wikis using their official install docs and link every source at the end.

To self-host a wiki with Docker, decide first who runs it, how you back it up, how people sign in and how it is reached over HTTPS. Then pick a wiki whose footprint fits that plan. Turtle runs as one container with SQLite and no other services. Docmost, Outline and Wiki.js need a separate database, and Docmost and Outline also need Redis.

What to decide before you run anything

The container is the easy part. The decisions around it decide whether your wiki is still healthy in a year.

Who runs it

Name one person who owns the wiki server. That person applies updates, watches disk space and restores backups. If nobody on your team wants this job, read the section on when not to self-host before you continue.

Backups

Decide where backups go and how often they run. A backup on the same disk as the wiki does not count. Plan one test restore before you invite the team, not after the first incident.

Sign-in

Check how your team signs in today. If your company requires SSO through Entra ID, Okta or Keycloak, filter the table above on that column first. Some wikis offer it in the free edition, some in a paid plan, and some not yet.

Reverse proxy and TLS

Most wiki containers speak plain HTTP on a local port. Put a reverse proxy such as Caddy, nginx or Traefik in front of it to terminate TLS. Point a subdomain like wiki.example.com at the proxy and let it fetch certificates.

Updates

Decide how you hear about new releases and when you apply them. Watching the GitHub releases page and updating on a fixed day each month works for most small teams. Pin image tags so an update only happens when you choose.

Walkthrough: self-host Turtle with Docker

Turtle is a self-hosted wiki where people and AI agents write documentation together. It ships as one binary with the web app built in. Data lives in SQLite plus an attachments folder in a data directory. There is no database server and no external service to run.

Turtle is in an early stage. Until version 1.0, the data format and API can change between releases. Read the release notes before every update.

1. Get the compose file

Images are published at ghcr.io/turtle-wiki/turtle. The repository at github.com/turtle-wiki/turtle provides a compose.yml. Copy it to the server into an empty folder.

2. Set the configuration

Turtle is configured with environment variables. The ones you will set first are the data directory, the public URL and your SMTP settings for invitation emails. Set them under environment: in compose.yml: TURTLE_PUBLIC_URL for the public address (it also enables OAuth for AI clients), TURTLE_SMTP_URL and TURTLE_MAIL_FROM for invitation and password-reset email, and TURTLE_DATA if you want a different data directory. The README lists every variable with its default.

Set the public URL to the HTTPS address your reverse proxy serves. AI clients connect to the built-in MCP server at that address plus /mcp, so it has to be reachable from where your team works.

3. Start it

docker compose up -d

Turtle listens on port 4100. Point your reverse proxy at that port and open your public URL in a browser. The first visit asks you to create the first account, which becomes the Workspace Admin.

4. Invite your team

Create an Area for each team or topic and invite members by email. Workspace Admins manage the workspace. Each Area has its own roles, for example Read, Write and Admin.

Not available yet: page-level or folder-level permissions, guests and public share links (planned for 0.4), and groups and OIDC/SSO (planned for 0.5). If you need any of these today, Turtle is not ready for you.

Other ways to run Turtle

If you prefer not to use Docker, prebuilt binaries exist for Linux (x86-64 and ARM64) and macOS on Apple Silicon. You can also build from source.

Backups

For Turtle, a backup means stopping Turtle and copying the data directory. Because everything sits in that one folder, a copy taken while Turtle is stopped is a complete backup.

docker compose stop
# copy the data directory to your backup target
docker compose start

With the provided compose.yml, the data directory is the turtle-data volume.

Schedule this with cron or your backup tool and keep several generations off the server. To restore, stop Turtle, put the copied data directory back and start it again.

As a second, human-readable safety net, you can export an Area or a subtree as a ZIP of Markdown plus attachments, or as PDF. This is useful before a large reorganisation. Treat it as a complement to the data directory backup, not a replacement.

For the other wikis, the backup covers more moving parts. Docmost, Outline and Wiki.js keep content in PostgreSQL, so you need a database dump plus any file storage. BookStack needs a MySQL or MariaDB dump plus its uploaded files.

Updates

To update Turtle, pull the new image and recreate the container:

docker compose pull
docker compose up -d

Turtle migrates its database automatically on start. Take a backup of the data directory first. Before 1.0 the data format can change between releases, so a backup is the only clean way back if an update goes wrong.

If you pin a version tag in compose.yml, change the tag first, then pull. The image tags are latest for the newest release, X.Y or X.Y.Z for a release line or a single release, and edge for the main branch.

The same pattern applies to the other wikis, with one extra step. When the app depends on PostgreSQL or Redis, those images also need updates, and a major PostgreSQL upgrade needs a dump and restore of its own.

When not to self-host

Self-hosting is a good fit when you have someone who owns the server and a reason to keep data on your own infrastructure. It is a poor fit in these cases:

  • Nobody on the team wants to own updates, backups and certificates.
  • Your company requires SSO and an audit trail from day one. Turtle has no OIDC yet. Check the paid plans of Docmost and Outline, or the free SSO options in BookStack and Wiki.js.
  • You need a wiki that is stable for years without data format changes. Turtle has not reached 1.0.
  • You need Confluence-style macros, whiteboards or databases. Turtle will not add content that cannot be expressed as Markdown.

A hosted version of Turtle has been announced, with a waitlist on turtle-wiki.app. There is no price or date yet.

What you give up

When you self-host, you give up someone else's on-call rotation. Security patches, disk monitoring and restore tests become your job. In return you control where the data lives, who can reach it and when it changes.

With Turtle in particular, you give up maturity. It has fewer features than Docmost, Outline, BookStack or Wiki.js today: no comments, backlinks or templates until 0.6, and no external security review until 1.0. What you get is the smallest footprint in this list and every feature in one AGPL-3.0 repository with no paid edition.

Frequently asked

What is the easiest self-hosted wiki to run with Docker?

Measured by moving parts, a wiki with an embedded database is the simplest. Turtle runs as one container with SQLite. Wiki.js also supports SQLite, though its docs recommend PostgreSQL for high availability.

Do I need PostgreSQL for a self-hosted knowledge base?

Not always. Docmost and Outline require PostgreSQL and Redis. BookStack needs MySQL or MariaDB. Turtle stores everything in SQLite inside its data directory.

Can I use single sign-on with a self-hosted wiki?

Yes, with most of them. BookStack and Wiki.js support SAML 2.0 and OIDC in their open source editions. Outline relies on SSO providers or email magic links. Docmost lists SSO in its paid Business plan. Turtle has no OIDC or SSO yet. It is planned for version 0.5.

How do I back up a Turtle wiki?

Stop Turtle, copy the data directory, and start it again. The data directory holds the SQLite database and all attachments.

Can AI assistants use a self-hosted Turtle wiki?

Yes. Turtle has a built-in MCP server at your address plus /mcp. Claude and other MCP clients connect by OAuth and never get more access than the member who connected them. Admins can switch AI connections off for the whole workspace.

Can I move from Confluence to a self-hosted wiki?

Yes. Turtle imports spaces from Confluence Data Center and Confluence Cloud, and you can try it in the demo. It reads the CSV or XML export with attachments: the page tree, attachments, page links, labels and mentions come across, some macros only approximately, and every import leaves an Import report and can be undone. See our Confluence migration guide.
