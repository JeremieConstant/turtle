How do you migrate from Confluence to an open-source wiki?

Export each space, import it, and fix what did not convert: a seven-step plan from pilot to cut-over.

Try the demo Ask Jérémie by email
Jérémie ConstantBuilds Turtle at novalutions. Updated 27 November 2026.

Short answer

We build Turtle Wiki, an open-source wiki that imports Confluence spaces. That makes us an interested party. This guide stays general where it can and says so where it is about Turtle.

To migrate from Confluence, you export each space, import it into the new wiki, and fix what did not convert. The export is the easy part. The work sits in cleanup, links, attachments and permissions.

Plan for a pilot space first. Keep Confluence read-only for a few weeks after cut-over. Expect macros, page restrictions and comments to need manual work in any Markdown-based wiki.

What Confluence lets you export

Both Confluence Cloud and Confluence Data Center can export a whole space. The formats and rules differ slightly.

Confluence Cloud. Space admins can export a space as PDF, CSV, HTML or XML. CSV, HTML and XML come as a ZIP archive, PDF as a single file. HTML exports leave out page comments and blog posts. Single pages can be exported as Word or PDF.

Confluence Data Center. You need the "Export Space" permission. A space can be exported as XML, HTML or PDF. The XML export is a full backup with pages, comments and attachments, but Atlassian only supports importing it into the same or a later Confluence version. HTML includes pages and attachments, with comments optional. PDF holds pages and images only.

In both editions, HTML and PDF exports contain only the pages you are allowed to view. Very large spaces can be slow to export or fail. Exporting smaller parts helps you find the page that causes the problem.

Which format to use. For a move to another wiki, the target tool decides. Some importers read the HTML export, others the XML export. PDF is useful as a frozen archive copy, not as a migration source.

If you run Data Center, the date matters. Atlassian ends Data Center on 28 March 2029. After that, products become read-only and security fixes stop. New Data Center subscriptions for new customers already stopped on 30 March 2026.

What usually does not survive a move to Markdown

Confluence stores pages in its own rich format with macros. Markdown is plain text with a small set of elements. Any Confluence to Markdown conversion loses something. These are the general expectations for any Markdown-based wiki, not a test of a specific tool.

  • Macros. Jira issue lists, page properties reports, include-page macros, dynamic tables of contents and most Marketplace app macros have no Markdown equivalent. At best they turn into static text or a placeholder.
  • Page restrictions. Restrictions on single pages often do not map to the target's permission model. Many wikis manage access per space or collection, not per page.
  • Comments. Inline and page comments are often dropped, or arrive as static text without threads.
  • Layouts and styling. Multi-column sections, panels, status lozenges, text colours and merged table cells usually flatten.
  • Page history. Most imports bring the current version of each page. Older versions often stay behind.
  • Users and mentions. User mentions point to Confluence accounts. They need a match in the new wiki or they become plain names.

Count these items during the inventory. A space full of Jira macros needs a different plan than a space of plain how-to pages.

A seven-step plan to migrate from Confluence

1. Inventory every space

List each space with its owner, page count, attachment size and last edit. Note which spaces use heavy macros or page restrictions. A spreadsheet is enough.

2. Archive dead content

Many Confluence sites carry years of pages nobody opens. Do not migrate them. Export those spaces to PDF or HTML, store the files, and leave them out of the move.

3. Pilot one space

Pick a mid-sized space with an engaged owner. Import it and compare page by page. Check headings, tables, code blocks, images and the page tree. Write down every fix you make by hand. That list becomes your checklist for the other spaces.

4. Check links and attachments

Click through internal links, especially links across spaces. Those break first. Compare attachment counts between source and target. Large files and unusual file types are worth a spot check.

5. Map permissions to Areas and roles

List who can read and edit each space today. Then decide how that maps to the new wiki. In Turtle, a Confluence space maps naturally to an Area, and access is set with roles per Area, such as Read, Write or Admin. Turtle does not yet support permissions on single pages or folders. That is planned for version 0.4. If a space depends on page restrictions, split the restricted pages into their own Area for now.

6. Cut over

Set a date. Tell users which spaces move and when. Freeze edits in Confluence, run the final export and import, and do one last link check. Move one group of spaces at a time if your site is large.

7. Keep Confluence read-only for a while

Do not delete anything on day one. Set the old spaces to read-only and add a notice that points to the new wiki. Collect reports of missing pages for a few weeks. Then archive the final export and switch Confluence off.

How the Confluence import works in Turtle

Turtle imports spaces from Confluence Data Center and from Confluence Cloud, and you can try it in the demo. A space comes in as a tree of Pages and Folders in an Area, in the same order. What else comes across:

  • Export format: export the space as CSV or XML, with its attachments. Confluence Cloud recommends CSV.
  • Macros: of the 54 kinds of Confluence content the import knows, 25 come across exactly, 25 approximately and 4 are left out. A macro it does not know becomes a placeholder naming the macro.
  • Attachments, page links, labels and mentions come across. Comments and earlier versions of pages stay in Confluence.
  • Page restrictions and space permissions are not imported. The Grants of the Area decide who may read and change the Pages.

Every import leaves an Import report as a Page, listing what to check and what was left out. You can undo an import from the Area's Imports menu.

Some things are certain. Every page in Turtle can be read and written as Markdown. Links between pages stay intact when you rename or move a page. You can export an Area or a subtree as a ZIP of Markdown plus attachments, or as PDF, and import Markdown. So your content does not get locked in a second time.

Turtle is in an early phase. Until version 1.0, the data format and API may change between releases. Plan your pilot with that in mind.

Other open-source wikis with a Confluence import

You have more than one option. Here is the status as we found it on each project's own pages.

  • Docmost (AGPL-3.0 open-source edition plus an Enterprise edition). Docmost imports the Confluence HTML export as a ZIP. Its release notes for version 0.21.0 list Confluence import as an Enterprise Edition feature. See our Docmost comparison.
  • XWiki (LGPL-2.1). XWiki imports Confluence XML exports through its Filter Streams Converter and Confluence XML module. Its documentation notes that macros need extra handling. A paid Confluence Migrator Pro adds migration of users, permissions and page history.
  • BookStack (MIT). BookStack states that it has no automated Confluence migration yet. Its REST API can automate parts of a custom move. See our BookStack comparison.

What you give up

Moving to an open-source wiki means owning more of the stack. You install, update and back up the software yourself. In Turtle, backup means stopping Turtle and copying the data directory.

You also give up features. Turtle will never support content that cannot be expressed as Markdown, so no Confluence-style macros, whiteboards or databases. Today Turtle has no comments (planned for 0.6), no groups or SSO (planned for 0.5) and no guest access or public share links (planned for 0.4). There is no plugin marketplace.

If your team depends on Jira macros or Marketplace apps, staying on Confluence Cloud may be the better choice. Weigh that honestly before you start.

Frequently asked

Can I export all of Confluence at once?

Exports in both Cloud and Data Center are built around spaces. For a move to another wiki, going space by space is also easier to control and to test.

What is the best Confluence export format for a migration?

The one your target wiki reads. Docmost uses the HTML export, XWiki the XML export. Turtle reads CSV or XML, with attachments. Keep a PDF export as an archive either way.

Can I convert Confluence to Markdown myself?

Yes. Community scripts convert HTML exports to Markdown files. Expect the same losses as with any importer: macros, layouts and comments. Turtle imports Markdown, so this is a fallback route.

Will my page restrictions carry over?

Usually not one to one. In Turtle, access is set per Area with roles, and the import does not bring page restrictions. Permissions on single pages are planned for version 0.4.

How long does a Confluence migration take?

It depends on the number of spaces, macros and restrictions. The pilot gives you a real estimate. Time the fixes for one space and multiply.

Do I have to move before Data Center ends?

Atlassian ends Data Center on 28 March 2029. Products become read-only then. Starting early leaves time for a pilot and a read-only period.
